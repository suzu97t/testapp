# 要件を点検する

役割は **答えを出すことではなく、問いを置くこと**。「こうすべきです」ではなく「これは誰が判定しますか」と聞く。業務の答えを知っているのは現場の人で、あなたではない。

## 手順

1. 機械的な点検結果を取る。

   ```sh
   ./bin/dandori.js tree
   ./bin/dandori.js lint          # 全件。1件だけなら: lint R-7
   ./bin/dandori.js list --type open
   ./bin/dandori.js list --type term
   ```

2. 機械が拾えないものを、自分の目で探す。観点は次の5つ。

   - **層の混在**：1つの文に「業務としてどうありたいか」「システムが何を担うか」「画面で何ができるか」「どの水準か」が混ざっていないか。混ざっていたら、分けたときに初めて見える未決がある。
   - **人がやる手順の支え**：人がやると決めた手順に、「誰が・いつ・何を見て・どう記録するか」があるか。「人がやるので要件はない」は誤り。
   - **言葉のずれ**：同じ言葉（在庫、顧客、完了…）が要件ごとに違う意味で使われていないか。用語集にあるか。あっても「含まないもの」が書かれているか。
   - **動いた後のこと**：止まったら業務は何時間耐えられるか。誰が・いつ・何を変えたかを後から追えるか。異常に最初に気づくのは誰か。
   - **受け入れ条件の偏り**：うまくいく場合しか書かれていない機能はないか。対象がゼロ、同時、途中で切れた、権限がない、取り消し。

3. 見つけたことを報告する。**重要な順に最大5つ**。全部を並べない。1つにつき次の形で。

   > **R-7 店員が本人確認をして引き渡しを記録できる**
   > 問い：家族が代わりに受け取りに来たとき、何を見せれば渡してよいですか？
   > なぜ聞くか：表の2行目（期限内・現物あり・本人確認できない）が空白です。

4. 人が「それは未決だ」と言ったものだけ、未決として登録する。要件に紐づける。

   ```sh
   ./bin/dandori.js add "代理の人が受け取りに来たとき、何を見せれば渡してよいか" --type open --about R-7 --ai
   ```

5. 人が答えを言った場合は、それを要件や受け入れ条件に反映してよいか確かめてから登録する。受け入れ条件はこう足す。

   ```sh
   ./bin/dandori.js add "代理の人が来た" --type criterion --parent R-7 --ai \
     --field given="取り置き中の注文があり、注文者本人ではない人が来店した" \
     --field when="注文番号を提示した" \
     --field then="店員は引き渡しを記録でき、記録に『代理』と残る"
   ```

   結果（then）に「正しく処理される」「エラーになる」と書かない。見えるもの・変わる数を書く。

## 守ること

- 登録は必ず `--ai` を付ける。
- 「作り始めてよいか」と聞かれたら、機能の層に受け入れ条件のないもの・空白の残る表・扱いの決まっていない例外の数を事実として伝える。可否の判断は人がする。
- 問題が見つからないときは、見つからなかったと言う。無理に指摘を作らない。
